# 独立任务管理

使用 `_tasks/` 下的独立目录管理每个任务。先形成有证据的任务分析和修改方案，再创建或更新任务记录。

## 基本边界

- 始终使用相对路径 `_tasks/<task-id>/`，并以其中的 `README.md` 作为任务入口。
- 把一次技能调用视为任务分析和任务记录操作；除非用户同时要求实现，否则不要修改业务代码。
- 默认使用中文记录；代码标识、命令和路径保留原文。
- 只调查与任务相关的最小范围，遵守 `AGENTS.md` 和 `README.md` 的入口阅读要求。

## 自动识别产品问题

不要把“创建任务”当作触发前提。用户要求解决、修复、排查、实现或优化某个问题时，先判断其结果是否会影响使用 `cc-connect` 的用户、运维人员或开发者可观察到的行为。

`cc-connect` 的对外行为面包括：CLI 子命令（`doctor`、`config`、`sessions`、`send`、`update`、`cron` / `timer`、`provider`、`web`）、前台运行与 `daemon`（systemd / launchd）运行形态、`config.toml` 配置项与多 workspace 绑定、平台适配器（Feishu / Telegram / Discord / Slack / DingTalk / WeCom / QQ / LINE / Weibo 等）的消息收发、卡片与流式渲染、Agent 适配器（Claude Code / Codex / Gemini / Cursor / OpenCode / ACP / Qoder 等）的会话与输出解析、会话生命周期与权限审批（`RespondPermission`）、i18n 文案、Web 管理端，以及选择性编译（build tag / Makefile）。

以下任一信号成立时，按产品问题自动调用本技能：

- 实际行为与期望、规格、历史正常行为或 `README.md` 描述不一致。
- 用户、测试或运维反馈缺陷、不可用、异常、兼容性或体验问题。
- 要求增加、补齐或调整功能、命令、配置项、平台 / Agent 支持、审批或渲染策略、部署方式。
- 技术改造会改变对外行为、支持范围、部署方式、兼容性、性能或稳定性。
- 用户要求直接修改代码来解决上述问题，即使没有要求分析方案或创建任务。

自动触发后：

1. 先匹配已有任务；没有明确匹配项时创建新任务并记录初始分析、方案、验收标准和验证计划。
2. 用户同时要求实现时，创建或更新任务记录后继续实现，不要把任务文档当作最终交付。
3. 实现和验证过程中持续更新同一任务目录，使状态与证据一致。

以下情况不凭本规则自动创建任务，但用户明确要求任务管理时仍应使用本技能：

- 仅回答概念、定位入口、解释代码或提供一般性建议。
- 仅做只读代码审查且没有匹配的已有任务、现状查询或状态汇报，没有要求修复。代码审查存在唯一匹配任务时只更新该任务，不创建新任务。
- 一次性的开发环境、命令使用或本地操作问题，不涉及产品交付行为。
- 格式整理、注释、纯文档或明确不改变产品行为的内部重构。

无法判断是否属于产品问题时，先做最小范围调查；有明确产品影响证据后自动调用，仍无法判断且创建任务会改变工作范围时再询问用户。

## 与 Git 工作流衔接

`cc-connect` 是单一 git 仓库，任务记录和代码改动写到同一仓库。默认工作在 `main` 分支；只有在确有并行改动冲突或需要保留稳定现场时，才切换或创建任务分支，不为形式创建分支或独立 worktree。

1. 先完成最小范围只读调查；此阶段可以搜索、阅读和检查 Git 状态，但不写文件。
2. 根据调查结果匹配已有任务 ID，或按创建流程生成新任务 ID。
3. 确认当前分支与工作区状态，在根仓库（本仓库）创建或更新 `_tasks/<task-id>/` 记录。
4. 用户同时要求实现时，再修改业务代码；不要为只创建/更新任务记录而提前改动业务代码。
5. 按 `AGENTS.md` 的 Pre-Commit Checklist 完成验证后再提交，提交信息简洁；只创建或更新任务记录、未改动代码时可一并提交。未获用户明确要求时不要主动 `git push`。

## 文档结构

默认只创建 `README.md`。内容明显复杂时，按需升级为：

```text
_tasks/<task-id>/
├── README.md          # 任务入口、摘要、状态、关键结论和下一步
├── analysis.md        # 详细调查、复现、根因推导和证据，可选
├── design.md          # 详细修改设计、接口、流程和方案决策，可选
├── review.md          # 代码审查范围、发现、检查证据和残余风险，可选
├── verification.md    # 复杂测试矩阵、环境和验证结果，可选
└── subtasks/          # 可独立执行和验收的子任务，可选
    └── NN-<slug>.md
```

按以下条件拆分，不要为了形式创建空文件：

- 简单任务：全部内容保留在 `README.md`。
- 调查过程、复现记录或根因证据较长：创建 `analysis.md`。
- 涉及多个模块、接口变化、关键流程或方案取舍：创建 `design.md`。
- 对已有任务执行代码审查：创建或更新 `review.md`，README 只保留结论摘要和链接。
- 任务最终变更范围包含任何代码：在标记为“已完成”前必须已创建或更新 `review.md`。
- 测试环境、版本组合或场景矩阵复杂：创建 `verification.md`。
- 存在多个可独立实现和验收的交付项：创建 `subtasks/NN-<slug>.md`。

遵守渐进披露：

- `README.md` 始终能够独立说明任务目标、当前状态、关键结论和下一步，并使用相对链接指向详情。
- 每条信息只保留一个权威位置。README 只摘要外部文档的结论，不复制完整分析、设计或测试记录。
- 更新任务时先读取 `README.md`，再只读取与本次操作有关且由 README 链接的详细文档。
- 超过约 100 行的详细文档应在开头提供简短目录，便于按需读取。

## 识别操作

根据用户意图选择一种操作：

- **创建**：识别出新的产品 Bug、需求或会影响产品行为的改造，或用户明确要求分析、设计方案或生成任务；无需用户说“创建任务”。
- **更新**：用户给出任务 ID、任务路径，或明确要求记录某个已有任务的进展。
- **审查记录**：代码审查与唯一已有任务匹配时，把完整报告写入该任务的 `review.md`，并更新 README 摘要。
- **总结**：把当前会话、Git 变更和验证结果合并到已有任务。

若用户明确指定任务目录，直接使用它。否则更新已有任务时，只检查 `_tasks/*/README.md`：

1. 根据标题、范围、涉及模块和当前会话匹配任务。
2. 只有一个明确匹配项时更新它。
3. 没有匹配项时创建新任务。
4. 多个任务同样可能匹配且无法可靠判断时，先询问用户，不要把内容写错任务。

代码审查是例外：没有匹配项时不创建任务；多个匹配项时可以继续只读审查，但在用户确认目标前不得写入任何任务目录。

## 代码审查记录

对已有任务执行代码审查后，按以下规则沉淀结论：

1. 只检查 `_tasks/*/README.md`，结合任务 ID、涉及模块、问题范围匹配任务。
2. 唯一匹配时，把完整报告写入 `_tasks/<task-id>/review.md` 并更新 README 摘要；用户明确要求完全只读时不写入。
3. 记录审查日期、被审范围（是否含未提交差异）、基线提交、审查结论、按严重级别排序的发现、已执行检查、未执行验证及残余风险。
4. 复审时维护同一个 `review.md`，标记之前发现为已解决、仍存在或被新证据推翻，不要按日期生成内容重复的报告。
5. README 只记录审查摘要、范围、发现数量、当前状态、下一步和 `review.md` 链接；详细发现只在 `review.md` 维护。
6. 没有发现问题时仍记录范围、检查证据和残余风险。审查通过不等于任务完成，不得绕过验收和验证门禁。
7. 写入后重新读取 README 和 `review.md`，确认链接、摘要、状态、下一步和详细结论一致。

## 创建流程

1. 理解用户原始描述，区分 Bug、新需求或技术任务。
2. 只读调查必要上下文：
   - Bug：记录现象、触发条件、期望行为、实际行为、影响范围和已知环境；定位最可能的原因与相关代码。
   - 新需求：记录业务目标、用户场景、当前行为、目标行为、范围和非目标；定位相关模块与现有实现。
   - 技术任务：记录动机、约束、受影响边界和可验证的完成条件。
3. 基于调查证据设计修改方案，明确改动位置（`core/`、`agent/*/`、`platform/*/`、`cmd/cc-connect/`、`config/`、`web/` 等模块，以及配置和文档）、关键逻辑、兼容性影响、风险和验证方法。把未经验证的判断标记为“待确认”，不要把猜测写成事实。
4. 生成任务 ID。
   - 格式为 `YYYYMMDD-<slug>`，日期使用当前本地日期。
   - `<slug>` 使用简短、可识别的英文小写 kebab-case，描述问题或目标，不使用笼统的 `bug`、`task`、`feature`。
   - 如果目录已存在，追加 `-2`、`-3` 等最小可用序号；不要覆盖已有任务。
5. 判断任务复杂度。创建 `_tasks/<task-id>/README.md`；只有满足拆分条件时才创建对应详细文档或 `subtasks/`。
6. 在 README 的“详细文档”中链接实际存在的文件；不存在的文件不要保留占位链接。
7. 用户同时要求实现时，在同一仓库继续实现并持续更新该任务目录。
8. 复查整个任务目录，确认另一个代理先读 README 即可理解任务，并能按链接获得实现所需细节。

## 更新流程

1. 先读取目标任务的 `README.md`，再按其中链接读取与本次更新有关的详细文档。
2. 保留仍然有效的上下文和已确认决策，只检查更新所需的最小代码与 Git 上下文。
3. 把新事实写入其权威文档，不要在 README 和详细文档间重复，也不要按时间机械追加重复叙述。
4. 当内容增长到满足拆分条件时，把详细内容迁移到对应文件，并在 README 保留结论摘要和链接。代码审查结论始终以 `review.md` 为权威位置。内容已不再需要独立维护时可以合并回 README，但不要丢失有效信息。
5. 更新 README 中的状态、关键结论、风险和下一步；被新证据推翻的内容应修正，并简短说明结论变化。
6. 准备把任务标记为“已完成”时执行“任务完成门禁”，并把文档更新判定写入 README。
7. 写入后重新读取受影响文档，检查链接、状态、结论和下一步是否一致。

## 任务完成门禁

任务只有在验收标准满足并记录验证证据后才能进入“已完成”。进入该状态前：

1. 读取任务 README、相关验证记录和当前任务对应的 Git 提交范围。
2. 判断任务的最终实际变更范围是否包含代码：Go 源码（`core/`、`agent/`、`platform/`、`cmd/`、`config/`、`daemon/`、`web/`）、脚本、构建 / 安装 / 部署配置、测试代码、内部重构及格式调整等都属于代码变更。
3. 包含代码变更的任务必须对最终实际变更范围做一次正式代码审查，包括已提交范围和未提交的任务差异，并在 `review.md` 记录范围、结论和证据。存在未解决的高严重度发现时，不得标记为“已完成”。
4. 不包含任何代码、脚本或配置变更的纯文档任务不触发正式代码审查门禁，但仍须在提交前完成 diff 自检和相应验证。
5. 判断是否存在用户或运维人员可感知的新功能、缺陷修复、兼容性、配置、部署或行为变化。
6. 用户可见行为发生变化时，必须同步更新对外文档（`README.md`、`README.zh-CN.md`），并更新 `CHANGELOG.md` 与 `CLAUDE.md` 顶部的“变更记录”；配置项变化同步 `config.example.toml`，平台 / Agent 相关变化同步 `docs/` 下对应文档。
7. 在 README 的“文档与发布”中记录 `README.md` / `README.zh-CN.md`、`CHANGELOG.md` / `CLAUDE.md`“变更记录”、`config.example.toml` 是否需要更新：需要 / 不需要 / 待确认，并给出依据。
8. 最终回复说明 `README.md` 和相关文档是否更新；未更新时说明原因。

纯文档、测试、格式调整和不改变外部行为的内部重构默认不需要更新用户文档，但必须记录判定原因。不要根据提交标题直接生成说明，应以任务范围、实际 diff 和验证证据为准。

## 任务记录模板

按任务实际情况删减章节，不要保留空章节。

```markdown
# <任务标题>

## 基本信息

- 任务 ID：`<task-id>`
- 类型：Bug / 新需求 / 技术任务
- 状态：待分析 / 方案已确定 / 实现中 / 待验证 / 已完成 / 已阻塞
- 创建日期：YYYY-MM-DD
- 涉及模块：<如 core/、platform/feishu、cmd/cc-connect、config/、web/>

## 原始问题

保留用户反馈或需求的核心语义；可区分“期望行为”和“实际行为”。

## 分析结论

记录足以指导任务的关键结论。详细内容较多时，改为结论摘要并链接 `analysis.md`。

## 修改方案

记录拟修改的模块、关键逻辑和范围。详细内容较多时，改为方案摘要并链接 `design.md`。

## 详细文档

- [问题分析](analysis.md)
- [详细设计](design.md)
- [代码审查](review.md)
- [验证记录](verification.md)
- [子任务](subtasks/)

只保留实际存在的链接。

## 验收标准

- 使用可观察、可判定的结果描述完成条件。

## 验证计划

- 记录核心测试场景（如 `go build ./...`、`go test ./...`、`make build`、`tests/blackbox` 用例、平台 / Agent 实测）。复杂测试矩阵放入 `verification.md`，此处保留摘要和链接。

## 当前进展

记录已完成的实现和验证事实，不写冗长逐文件流水账。

## 文档与发布

- README / README.zh-CN 更新：需要 / 不需要 / 待确认
- CHANGELOG / CLAUDE.md 变更记录更新：需要 / 不需要 / 待确认
- config.example.toml 更新：需要 / 不需要 / 待确认
- 用户可感知变化：<只记录已经实现并验证的行为>
- 功能边界：<记录限制或不承诺的能力>
- 对应提交：<任务提交或合并提交>

## 风险与待确认项

- 记录兼容性、回归风险、外部依赖、阻塞点和未决问题。

## 下一步

- 写出一个可立即执行的动作。
```

## 状态规则

- `待分析`：关键信息不足，尚不能给出可靠方案。
- `方案已确定`：分析与修改方案已足够支持实现。
- `实现中`：业务代码已开始修改，但尚未完成全部验证。
- `待验证`：实现完成，仍缺少必要测试或目标环境验证。包含代码变更时，进入该状态前应先完成针对当前实际变更范围的代码审查。
- `已完成`：验收标准全部满足，记录了验证证据，并通过任务完成门禁。
- `已阻塞`：存在当前无法推进的外部条件，并明确写出解除条件。

不要仅因代码已修改就标记“已完成”，也不要把计划执行的测试写成已经通过。

## 质量检查

完成前确认：

- 一个任务只占用一个独立目录。
- 简单任务没有不必要的空白详细文档；复杂任务已按拆分条件组织。
- 标题和任务 ID 能区分该任务，不依赖完整会话才能理解。
- 分析结论可追溯到用户描述、代码、配置、日志或测试证据。
- 修改方案具体到模块或路径，并包含边界和风险。
- 验收标准可观察、可测试，不使用“正常工作”等模糊描述。
- 当前状态与实际实现、测试证据一致。
- 已完成任务包含文档与发布判定；用户可见行为变化已同步到 `README.md` 与 `CHANGELOG.md`，并更新 `CLAUDE.md` 顶部的“变更记录”。
- README 中的相对链接有效，且同一信息没有在多个文件重复维护。
- 包含代码变更的已完成任务已有针对最终实际变更范围的代码审查报告，`review.md` 保存完整发现、README 只保留摘要；纯文档任务记录不触发依据；没有匹配任务的只读审查没有擅自创建任务。
- 未完成任务有明确、可执行的下一步。
